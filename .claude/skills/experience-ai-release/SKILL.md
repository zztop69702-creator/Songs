# 경험곱하기AI 수정 → 검증 → 배포

이 앱은 사용자(송유성, 1인 기술 전문가)가 승인한 **완성 자산**이고, 사용 대상은 50~60대다. 그래서 이 절차의 핵심은 두 가지다. 하나는 **고친 것 말고는 아무것도 바뀌지 않았음을 숫자로 보이는 것**이고, 다른 하나는 **사용자가 보는 화면에서 실제로 되는지 확인하는 것**이다. 앱 구조와 계산 규칙은 `references/app-map.md` 에 있다. 고칠 곳을 찾기 전에 읽는다.

## 대화 원칙 (사용자 지침에서 온 것)
- 한국어 존댓말, **결론부터**. 사용자는 오타가 잦으니 뜻을 바로잡아 이해하고, 고친 표기를 한 줄로 알린다(예: '에어젼시' → 에이전트로 이해).
- 확인한 사실, 추정, 의견을 구분한다. 수행하지 않은 검증을 했다고 말하지 않는다. Windows 실설치처럼 여기서 못 하는 것은 '검증하지 못함'으로 적는다.
- 사용자 의견이 틀렸다고 판단되면 근거와 함께 반대하고 대안을 낸다(예: 칸별 사람 검토 대신 기준을 글로 남긴 AI 추론 검증).
- 사업 관점(1인 전문가 홈페이지, 공공 영업의 법적 요건 '확인 필요')을 필요할 때 짧게 덧붙인다.

## 승인 기준: 바로 고칠까, 먼저 물을까
| 종류 | 처리 |
|---|---|
| 재현되는 오류, 오타, 문구 수정, 사용자가 형식을 정해 준 요청 | 바로 최소 수정 → 검증 → 보고 |
| 계산식·추천 규칙·학습 시간·결과카드 양식·저장 데이터 구조 변경 | 효과를 숫자로 보여 주는 안(A/B)을 내고 승인 후 진행 |
| 디자인·화면 배치 변경 | **시안 이미지를 먼저 만들어 보여 주고** 승인 후 진행 (사용자는 그림으로 판단한다) |
| 사용자가 "제안하고 승인받고 진행해"라고 한 경우 | 무엇이든 커밋·배포 전에 멈추고 승인을 받는다 |

질문은 `AskUserQuestion` 으로 2~4개 선택지와 (권장) 표시를 붙인다. 사용자가 이미 "진행해", "너의 권장안대로"라고 했으면 다시 묻지 않는다.

## 절차

### 1. 재현부터
증상 신고(캡처 포함)가 오면 고치기 전에 **같은 상태를 만들어 재현**한다. 사용자 캡처의 문구로 상태를 읽어 `localStorage['experience-ai-map-v1']` 에 넣고 Playwright 로 클릭한다(예: `scripts/verify_clicks.js` 를 복사해 상태만 바꿈). 먼저 볼 것:
- **머리글 '빌드 MMDD-HHMM'**이 최신 배포와 다르면 옛 버전이다. 코드를 고치기 전에 새로고침(Ctrl+Shift+R)이나 재설치를 안내한다. 화면 문구가 현재 코드에 없는 문구인지 `grep` 으로도 확인한다.
- 움직임이 없다는 신고는 Windows '애니메이션 효과 끔'(prefers-reduced-motion)일 수 있다 → '움직임 켜기' 버튼을 안내한다.
원인을 사용자에게 표로 설명한다(사용자 화면 / 실제 원인 / 조치).

### 2. 수정
- 수정 전 `src/app.html` 을 작업 폴더(scratchpad)에 복사해 둔다.
- 여러 곳을 고칠 때는 **"정확히 1곳에만 있는 문자열을 바꾸고, 아니면 멈추는"** 파이썬 스크립트로 바꾼다(`assert t.count(a) == 1`). 스크립트 파일은 Write 도구로 만든다. 복잡한 따옴표가 든 heredoc 은 안전 검사에 걸릴 수 있다.
- 바꾼 이유를 한국어 주석으로 한 줄 남긴다. 새 불변 조건은 `console.assert` 로 넣는다. 그러면 검사 스크립트가 위반을 오류로 잡는다.
- 저장 키(`experience-ai-map-v1`), 역량 번호, 설치 데이터 폴더(`%LOCALAPPDATA%\AI다음행보`)는 바꾸지 않는다. 바꾸면 사용자 입력값이 사라진다.

### 3. 검증 (매번 전부)
```bash
bash .claude/skills/experience-ai-release/scripts/check_all.sh /home/user/Songs <scratchpad>/check
```
통과 기준:
| 검사 | 통과 |
|---|---|
| smoke (1~10단계 전체, PC 1366 · 휴대폰 390) | `ERRORS: []` 두 줄 |
| regress (같은 입력 4가지의 결과카드·지침문·학습표를 HEAD 와 줄 단위 비교) | `diffs 0`. 의도한 변경이면 그 줄만 다르고, 보고에 '의도한 차이'로 적는다 |
| layout_flow (1280·1366·1920·2560) | `xover 0`, `docScrollY 0`, 흐르는 점 100% 선 위, 1쪽 스크롤은 작게(≈40px 이하) |
| verify_clicks (배포 파일, 보통·움직임 줄이기 PC) | 지도 비우기 → 출발점 없음·빛줄기 0, 내 목표 보기 → 복원, 움직임 켜기 후 점 이동, 오류 0건 |
| finale | '정의 완성' 표시, 오류 0 |
| download_button | 버튼 보임, ZIP 머리글 `50 4b 3 4`, 설치된 앱에서는 버튼 숨김 |

새 기능은 그 기능 전용 짧은 Playwright 테스트를 하나 더 써서 **전후 숫자**를 보인다(예: 도움 버튼을 켰을 때 판단과 시간 기준이 어떻게 바뀌는지). 화면이 바뀌는 수정은 캡처를 직접 보고(Read) 확인한다. 사용자에게 보낼 캡처는 `deviceScaleFactor: 2` 로 찍는다.

전문가·역량 연결을 바꿨다면 `node scripts/linkage_report.js <src/app.html> ai-next-step/검증보고서_역량연결.md` 로 보고서를 다시 만들고, `scripts/reach.js` 로 추천 도달 수를 확인한다.

### 4. 빌드
`python3 -I build.py` 를 실행하면(배포할 때만) `dist/` 에 `.bat`(ASCII 전용, 앱·스크립트·아이콘 내장), `.zip`, `online.html`(설치 ZIP 내장)이 생기고, 머리글에 '빌드 MMDD-HHMM'(한국시간)이 찍힌다. check_all.sh 는 결과 폴더에 시험용으로만 빌드하므로, 배포할 때는 이 명령을 따로 실행한다.

### 5. 커밋·푸시
지정 브랜치에서 커밋한다. 메시지는 영어 제목 + 핵심 변경 목록이고, 끝에 세션이 지정한 attribution 줄을 붙인다. 푸시는 `git push -u origin <branch>` 이다. 실패하면 네트워크 오류일 때만 2·4·8·16초 간격으로 재시도한다.

### 6. 배포
- 온라인 앱: `Artifact` publish, `file_path` = `ai-next-step/dist/online.html`, `url` = `https://claude.ai/artifact/PEsnd7h9HVSND2Abu17tbs`. capabilities 는 생략하면 기존 `downloads` 가 유지된다.
- 설치 파일: `SendUserFile` 로 `dist/경험곱하기AI_v1.8_설치.zip` 을 보낸다(display attach). 화면이 바뀌었으면 확인 캡처도 함께(render) 보낸다. 한글 파일명이 깨지면 영문 이름으로 복사해 보낸다.
- 버전 번호(v1.8)는 사용자가 요청할 때만 올린다. 올릴 때는 `build.py` 의 VER, `app.html` 의 `.ver`, `install.ps1` 의 `$ver` 를 함께 바꾼다.

## 이 앱에서 겪은 함정
- 옛 버전 화면으로 신고 → 빌드 번호로 판별 (실제 사례: '지도 비우기 안 됨'이 옛 버전이었다).
- 목표(①②③)는 2쪽 5단계 답이다. '지도 비우기'는 1쪽만 비우는 탐색 모드(`mapFree`)이고, 결과카드는 그대로다.
- 칸 채움은 **가로(width)**다. 높이로 재는 테스트는 0으로 나온다.
- 앱 전체 확대(`zoom`)와 캔버스 축소가 겹쳐도 선 좌표는 화면 px 로 계산된다. 선이 칸과 어긋나면 `drawWires` 의 기준 사각형을 의심한다.
- 반복 실행되는 흐름 점(`circle.tick`)과 빛기둥 점(`circle.col`)은 테스트에서 구분한다.
- 사용자에게 보이는 '도움·돌발' 버튼은 모든 단계에서 눌러야 한다(전체 지도 시연 중에만 잠금).
